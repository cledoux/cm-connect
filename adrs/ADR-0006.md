# ADR-0006: Diff-Scoped Finding Filtering and Dynamic Matrix Generation Strategy for GitHub Actions (filter_findings.jq)

- **Status:** accepted
- **Date:** 2026-08-21
- **Decision Makers:** Charles LeDoux (ledoux@google.com)

**Shortlink:** go/cm-connect-adr-0006

## Context and Problem Statement

In \`cm-connect\`, the GitHub Actions PR review workflow (\`cm-pr-workflow\` per
[cm-pr-workflow proposal](../openspec/proposals/cm-pr-workflow/proposal.md))
orchestrates a two-stage CI/CD pipeline:

1. **Scanning Stage (\`scan\`):** Executes \`cm-runner find\` against the pull
   request codebase, capturing findings in \`.codemender-out/findings.json\`.
1. **Parallel Remediation Stage (\`fix\`):** Dispatches concurrent matrix jobs
   (\`strategy: matrix\`) where each worker executes \`cm-runner fix\`
   statelessly on an individual finding.

Full-repository vulnerability scanning inherently detects pre-existing security
issues in untouched legacy files. Attempting automated remediation on legacy
code during a pull request introduces severe drawbacks:

1. **Developer Review Fatigue:** PR authors are spammed with review comments and
   remediation suggestions on legacy code they did not author or modify.
1. **Wasted CI/CD Runner Minutes:** Parallel matrix jobs are spawned for
   un-scoped findings, exhausting runner concurrency quotas.
1. **Diff-Boundary API Rejections:** GitHub's Pull Request Review API (\`POST
   /repos/{owner}/{repo}/pulls/{id}/reviews\`) rejects inline review comments
   with HTTP \`422 Unprocessable Entity\` when comment line coordinates fall
   outside the pull request's diff hunks.

To eliminate noise, the workflow must cross-reference findings against
\`commit.diff\`, discard out-of-diff findings, sort remaining findings by
severity (\`CRITICAL\` > \`HIGH\` > \`MEDIUM\` > \`LOW\`), throttle dynamic
matrix size to top $M$ items, and emit a structured JSON payload for GitHub
Actions \`strategy: matrix\`.

How should \`cm-connect\` implement this diff filtering and matrix generation
step across heterogeneous target repositories adopting CodeMender?

## Decision Drivers

- **Language-Agnostic Portability in Target Repositories:** The workflow
  template (\`github-actions/workflows/codemender.yml\`) is designed to be
  copied into arbitrary target repositories (e.g. pure Go, Rust, C++, Java,
  Node.js, Python) via \`install.sh\`. The filtering step MUST NOT force
  adopting repositories to install extra language runtimes (such as Python or
  Node.js) or manage language-specific dependency managers (\`pip\`, \`npm\`).
- **Zero Toolchain / Runtime Setup Overhead:** Must execute instantly without
  requiring prerequisite setup actions (e.g. \`actions/setup-python\`,
  \`actions/setup-node\`, \`pip install\`, \`virtualenv\` configuration) in
  target workflows.
- **Universal Pre-Installation on Standard Hosted Runners:** Must run out of the
  box on standard GitHub-hosted runner environments (\`ubuntu-latest\`,
  \`macos-latest\`, \`windows-latest\`).
- **Sub-Millisecond Startup Latency:** Must eliminate interpreter cold-start
  overhead (\<1ms execution) to keep CI step latency negligible.
- **Native Pipeline & \`$GITHUB_OUTPUT\` Composability:** Must seamlessly
  process JSON data streams from files or standard input and format compact JSON
  strings (\`jq -c\`) for GitHub Actions \`$GITHUB_OUTPUT\`.
- **Diff-Scoped Interval Precision:** Must parse unified diff file headers
  (\`+++ b/<path>\`) and hunk headers (\`@@ -old,count +new_start,new_count
  @@\`) to calculate exact inclusive line intervals \`\[start, start + count -
  1\]\` and accurately test finding intersections.
- **Supply Chain & Dependency Minimization:** Zero third-party library
  dependencies, eliminating supply chain risk and maintenance burden.

## Considered Options

- **Option 1: Standalone Declarative \`jq\` Script
  (\`github-actions/scripts/filter_findings.jq\`) — (Chosen)**
- **Option 2: Standalone Python Script
  (\`github-actions/scripts/filter_findings.py\`)**
- **Option 3: Inlined JavaScript / GitHub Script Action
  (\`actions/github-script\`)**
- **Option 4: Host-Compiled Go CLI Binary / Subcommand (\`cm-runner filter\`)**

______________________________________________________________________

### Option 1: Standalone Declarative \`jq\` Script (\`github-actions/scripts/filter_findings.jq\`) — Chosen

Implement a standalone \`jq\` filter script taking \`--rawfile diff
commit.diff\` and findings JSON: \`\`\`bash jq --rawfile diff commit.diff
--argjson max_findings 10 -f github-actions/scripts/filter_findings.jq
findings.json \`\`\`

- **Mechanism:**
  - Implements \`parse_diff($diff_text)\` to parse \`commit.diff\` line-by-line,
    tracking active files and converting hunk headers (\`@@ ... +start,count
    @@\`) into interval objects \`{file, start, end}\`.
  - Filters findings array by verifying whether \`[StartLine, EndLine]\`
    intersects any diff interval for that file.
  - Sorts retained findings descending by severity rank (\`CRITICAL\`=4,
    \`HIGH\`=3, \`MEDIUM\`=2, \`LOW\`=1).
  - Throttles output array to top \`$max_findings\` / \`$max\` items.
  - Maps each finding to the GitHub Actions matrix item schema: \`{finding_id,
    file_path, start_line, severity, title, payload}\`.
  - Emits \`[]\` on zero matches or empty diff inputs.
- **Evaluation:**
  - *Good, because* \`jq\` is pre-installed out of the box on all standard
    GitHub Actions runners (\`ubuntu-latest\`, \`macos-latest\`,
    \`windows-latest\`).
  - *Good, because* 100% language-agnostic: adopting repositories in pure Rust,
    Go, C++, or Java require zero Python/Node setup in CI.
  - *Good, because* execution latency is instantaneous (\<1ms) with zero memory
    overhead.
  - *Good, because* zero supply chain dependencies (\`requirements.txt\`,
    \`package.json\`, virtualenvs).
  - *Good, because* compact single-file footprint (~70 lines of declarative
    code).
  - *Neutral, because* requires developers maintaining the script to be familiar
    with \`jq\` functional DSL syntax.

______________________________________________________________________

### Option 2: Standalone Python Script (\`github-actions/scripts/filter_findings.py\`)

Implement a Python 3 script using standard library modules (\`sys\`, \`json\`,
\`re\`, \`argparse\`).

- **Evaluation:**
  - *Good, because* Python syntax is widely understood and standard regex
    libraries are familiar.
  - *Bad, because* target repositories in non-Python ecosystems (pure Go, Rust,
    C++) are forced to add \`actions/setup-python@v5\` and manage Python runtime
    versions in their CI workflows.
  - *Bad, because* Python interpreter initialization introduces ~50–100ms
    startup latency per invocation.
  - *Bad, because* risk of environment collision or Python version divergence
    across target runner environments.

______________________________________________________________________

### Option 3: Inlined JavaScript / GitHub Script Action (\`actions/github-script\`)

Implement the diff parser and matrix generator in JavaScript using
\`actions/github-script@v7\` or a Node.js script.

- **Evaluation:**
  - *Good, because* Node.js runtime is built into GitHub Actions runners.
  - *Bad, because* inlining complex diff parsing logic into workflow YAML
    creates massive YAML bloat and poor readability.
  - *Bad, because* running via \`actions/github-script\` tightly couples the
    filtering logic to GitHub Actions runner internals, making local CLI testing
    outside of GitHub Actions cumbersome.

______________________________________________________________________

### Option 4: Host-Compiled Go CLI Binary / Subcommand (\`cm-runner filter\`)

Add a \`filter\` subcommand to \`cm-runner\` or build a separate compiled Go
tool.

- **Evaluation:**
  - *Good, because* written in Go, sharing existing data models.
  - *Bad, because* \`cm-runner\` is packaged and executed inside Docker; running
    it directly on the host runner VM before matrix dispatch would require
    compiling and releasing architecture-specific host binaries
    (\`linux-amd64\`, \`linux-arm64\`, \`darwin-amd64\`, \`darwin-arm64\`).
  - *Bad, because* introduces complex multi-platform binary release, download,
    and caching overhead into the workflow template.

______________________________________________________________________

## Decision Outcome

Chosen option: **Option 1: Standalone Declarative \`jq\` Script
(\`github-actions/scripts/filter_findings.jq\`)**.

### Justification

Option 1 delivers the lowest possible adoption friction, zero toolchain
prerequisites, universal CI runner compatibility, and instant startup execution
without adding language runtime dependencies to adopting codebases.

## Confirmation & Verification Strategy

Compliance and correctness are verified via automated native Go integration
tests in \`tests/integration/workflow_filter_test.go\` (\`//go:build
integration\`):

1. **In-Diff Finding Retention Test:**
   - Execute \`filter_findings.jq\` with \`tests/fixtures/workflow/commit.diff\`
     and \`findings_in_diff.json\`.
   - Assert all matching findings are retained and formatted with \`{finding_id,
     file_path, start_line, severity, title, payload}\`.
1. **Out-of-Diff Exclusion Test:**
   - Execute with \`findings_out_of_diff.json\`.
   - Assert output is an empty array (\`[]\`).
1. **Mixed Severity Sorting Test:**
   - Execute with \`findings_mixed.json\`.
   - Assert out-of-diff findings are discarded and in-diff findings are sorted
     descending by severity: \`CRITICAL\` $\\to$ \`HIGH\` $\\to$ \`MEDIUM\`.
1. **Max Concurrency Throttling Test:**
   - Execute with \`--argjson max 2\`.
   - Assert output is truncated to exactly the top 2 findings.
1. **Empty Diff & Empty Findings Resilience Tests:**
   - Execute with empty \`commit.diff\` or empty \`[]\` findings input.
   - Assert output is \`[]\` with zero errors.
